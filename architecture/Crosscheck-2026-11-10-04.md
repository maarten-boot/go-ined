## 2. Code → Spec (bugs found in the code)

| # | Sev | Finding | Evidence | Proposed fix |
|---|-----|---------|----------|--------------|
| C1 | L | **Probe errors are silent.** A probe that fails with an error (for example "network is unreachable" when there is no route) counts as probed and not found. A whole unreachable range ends `done` with `found: 0`, and nothing tells the user why | `discovery.runJob`: `r.err` is only checked for cancellation | Count failed probes in the job (`errors`), and keep the first error message in `error` (the state stays `done`). Log one warning per job |
| C2 | L | **Lookups and pings that wait for a slot each hold a goroutine.** `dnsname` starts one goroutine per due host, which then waits for the concurrency semaphore. After a /16 discovery that could be up to 65,534 waiting goroutines (~250 MB). `monitor` works the same way, but it only starts one round per host per interval | `dnsname.Run`: `go lookup(...)` before `sem <-` | Take the semaphore in the scheduler loop and start the goroutine only when a slot is free; due hosts wait in the loop. Same change in `monitor` for symmetry |
| C3 | L | **`Start` and `Close` race on the WaitGroup.** A `Start` that passed the `closed` check just before `Close` calls `wg.Add(1)` after `Close`'s `wg.Wait()` returned. That's harmless today (the job's context is already cancelled and it saves nothing), but it's the documented `WaitGroup` misuse | `discovery.Start`: `m.wg.Add(1)` after the lock is released | Do `wg.Add(1)` under the lock, together with the reservation, and `Done` on every exit path |
| C4 | L | **`discovery.rate` has no upper bound.** `time.Second / rate` is 0 for a rate above 10⁹, and `time.NewTicker(0)` panics | `config.Validate`: `rate >= 1` only | Validate `1 ≤ rate ≤ 100000` |
