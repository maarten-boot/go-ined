## 2. Code → Spec (bugs found in the code)

| # | Sev | Finding | Evidence | Proposed fix |
|---|-----|---------|----------|--------------|
| C1 | M | **In a PATCH, `null` on a field that can't be null silently sets it to its zero value.** <br>• `{"monitored": null}` turns monitoring **off**. <br>• `{"x": null}` moves the item to x = 0. <br>• `{"collapsed": null}` expands the group. <br>• `{"order": null}` sets a view's order to 0. <br>• `{"name": null}` gives "must not be empty", which is the right result for the wrong reason. <br>This has been in `apitypes.Opt` since M1; it was found while probing `ViewPatch` | Probe: `PATCH /hosts/2 {"x":null}` → 200, x = 0; `PATCH /views/2 {"order":null}` → 200, order 0. `Opt.UnmarshalJSON` stores the zero value on `null` | `Opt[T].UnmarshalJSON` rejects `null` unless `T` is a pointer (only `parent_id`, where `null` means the root). The request then fails with 400 `invalid_argument` ("field must not be null"). Add the case to the SPEC-504 table, and add a test for every PATCH type |
| C2 | L | **`inedctl view show` exits 0 when its second request fails.** The command fetches the view, then the view's map. If the map request fails (for example, the view was deleted in between), the error goes to stderr but the exit code is 0 | `viewShow`: the `ViewMap` error is printed, not returned | Return the error, so the exit code follows SPEC-903 |
| C3 | L | **`group list` without `--view` mixes all views with no way to tell them apart, and `group show` doesn't show the view.** A custom-view group at the root looks like a network-view root group | Probe: group 4 "Shelf" (view 2) is listed among the network groups with PARENT `root` | Add a VIEW column to `group list` and a `View:` row to `group show`; update the SPEC-902 column list |
| C4 | L | **`inedctl view place <v> <h> --x X --y Y` without `--parent` moves the host to the view's root.** This follows the API (`PUT`, where a missing `parent_id` means the root), but the usage text doesn't say so, and repositioning a host inside a group is a natural thing to try | Usage: `view place <view-id> <host-id> [--parent ID] [--x X --y Y]` | **Needs the user's decision:** <br>(a) document it in the usage text and SPEC-124: "without --parent: the view's root" (recommended, because the CLI stays a thin layer over the API); <br>(b) `inedctl` reads the current placement from `GET /map?view=` and keeps the parent when `--parent` is missing |

Checked and found consistent with §4b:
- **Views and groups:** view 1 can't be deleted (409); duplicate and empty view names are rejected; new views go last. A CIDR in a custom view, a parent in another view, and a host `PATCH` to a custom-view group all give 400.
- **Placements:** placing a host in view 1 gives 400; an unknown host, an unknown view and an unplaced host give 404; giving only `x` or only `y` gives 400.
- **Events:** cascade in a custom view emits `placement.deleted` and `group.deleted` per item and no `host.deleted`; deleting a view emits a single `view.deleted`.
- **Status:** `emitGroupStatus` uses `AggregateAll`, so a status change reaches groups in every view.
- **Discovery:** only puts hosts in the network view. A target parent in a custom view gives 400 (from `CreateGroup`).
- **Storage:** `DeleteHost` and network-view cascades delete the host's custom-view placements in the same transaction.

## 6. Other suggestions

- **I1:** `inedctl host show` (and later the GUI's details panel) can't show which custom views a host appears in. The only way to find out is to read every view's map. Recommended: decide in M5, when the GUI needs it, whether host JSON gets a `views` list.
- **I2:** View names are unique but case-sensitive: "Networks" and "networks" can both exist. Recommended: leave it as it is.
- **I3:** No benchmark covers `AggregateAll`, which every ping batch runs for every view. With about 5,000 hosts and a few views it should be cheap, but this hasn't been measured. Recommended: add a benchmark alongside TC-708 (5,000 hosts) in M5.
