## 2. Code → Spec (bugs found in the code)

| # | Sev | Finding | Evidence | Proposed fix |
|---|-----|---------|----------|--------------|
| C1 | H | **The GUI can't keep up with a burst of changes and holds on to about 700 MB.** <br>• Every in-place event (`host.status`, `host.updated`, `group.status`) lays out the whole view again and rebuilds every canvas object near the visible area. <br>• So a burst queues seconds of work on the UI thread, and the window stops reacting meanwhile. <br>• A realistic case: a switch fails, hundreds of hosts go `down` at once, and `group.status` events follow | **Probe 1:** 500 events with 5,000 hosts took 2.3 s (4.6 ms each). <br>**Probe 2:** with 2,046 hosts and about 1,600 changes in 12 s, RSS went from 236 MB to 947 MB. The CPU stayed busy for about 20 s after the changes stopped, and the memory wasn't released within 90 s | **Coalesce the redraws:** an event only marks its view as changed. One redraw per view is queued behind the events already waiting, and it runs at most every 100 ms. <br>**Reuse canvas objects** between redraws instead of creating new ones each time, so Fyne's text-texture cache doesn't grow with every redraw. <br>**Add a test** (TC-714): 1,000 status events on 5,000 hosts are handled in under 1 s, with at most a few layouts. Repeat probe 2, with this target: the backlog is gone within 1 s, and RSS grows by less than 100 MB |
| C2 | M | **A view created or renamed while the GUI (re)loads the views can be missed until the next reconnect.** <br>• `loadAll` fetches `GET /views` and then replaces the list. <br>• A `view.*` event applied in between is overwritten by the older list. <br>• Maps already have this protection (`Gen`); the list of views doesn't | `gui.go` `loadAll` → `model.SetViews(vs)` | Give the list of views a generation counter, as maps have. If it changed during the fetch, fetch again. Add a test in `mapmodel` |
| C3 | L | **`details.fill` for a group reads `g.maps[d.view].Nodes()` without checking for nil.** No path reaches it today: the details are cleared when the current view goes. But a late answer for a deleted view would crash the GUI | `panels.go` `fill` | Check for nil (counts "-") |
| C4 | L | **Dead code:** `zoomLabel` is never used, and `contrastOption` has two identical branches | `gui.go`, `panels.go` | Remove them, or use `zoomLabel` for I1 |
| C5 | L | **Untested GUI paths** (see §1): find dialog, custom-contrast dialog, context menu, toolbar zoom actions, most of `details.onEvent` | Coverage | Headless tests for each: type in the find box and pick a result; enter a valid and an invalid custom ratio; context menu items enabled or disabled; toolbar zoom; details follow `host.updated`, `group.status` and `*.deleted` |

## 6. Decisions for the user

- **D1 (open since M5):** in Max contrast, buttons have the same white background as the window, so only their text shows.
  - (a) Give buttons a black 1-pixel border in Max (recommended: they look like buttons again, and it's still black and white only).
  - (b) Leave it.
- **D2 (open since M5):** items placed close together can overlap an expanded frame.
  - (a) Dragging in M6 is enough for now (recommended).
  - (b) Also add a "tidy up" action for a group in M6.
- **D3 (S2):** large groups form tall strips, because members are placed in rows of 10.
  - (a) Make the server's row width grow with the group: about the square root of the number of members, at least 10 and at most 50 per row. Only new members are affected (recommended; small change in `FreePosition`).
  - (b) Lower the minimum zoom below 10 %.
  - (c) Leave it.

## 7. Other suggestions

- **I1:** show the current zoom (for example "100 %") in the toolbar, using `zoomLabel` (C4). Recommended.
- **I2:** a single click selects with a short delay (about 300 ms). Fyne waits that long to tell a click from a double click on widgets that handle both. This can't be avoided without giving up double-click (SPEC-703); no change.
- **I3:** `staticcheck` and `govulncheck`, and raw-socket ICMP (M7).
