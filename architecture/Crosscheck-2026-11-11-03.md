## 2. Code → Spec (bugs found in the code)

| # | Sev | Finding | Evidence | Proposed fix |
|---|-----|---------|----------|--------------|
| C1 | M | **The discovery dialog can miss the end of its own job.** <br>• The GUI starts following a job only when the `POST /discovery` answer arrives. A small range can finish before that, and the `discovery.finished` event is then ignored. <br>• The dialog stays at "0 of 2 probed", "Start" stays disabled, "Cancel job" stays enabled, and the status bar never reports the result | **Probe 2:** 1 of 20 jobs on a /30 was missed. The dialog stayed at "discovery 10.113.0.0/30: 0 of 2 probed, 0 found" | After `StartDiscovery` returns, fetch the job once more (`GET /discovery/{id}`) and show that state. Also keep the last discovery events of unknown jobs for a few seconds, so an early `finished` can be matched. Add a test that runs many tiny jobs |
| C2 | M | **The discovery dialog's progress bar fails the contrast rules (SPEC-002, 003, 709).** <br>• Fyne draws the empty part of a `ProgressBar` as the primary colour at 50 % transparency, with the percentage in white. <br>• In AA that is white on pale blue, about 2:1. In Max it adds grey, which isn't black or white | Probe 3 screenshot ("0%" in white on pale blue); Fyne `widget/progressbar.go` `progressBlendColor` | Draw the bar ourselves: a track with a `Border` outline, a `Primary` fill, and no text inside it (the text below already says "n of m probed"). Add a test that Max uses only black and white for it |
| C3 | M | **`PATCH /groups/{id}` with only `x`/`y` now moves the group's contents too, and emits `group.moved`.** <br>• SPEC-508 asks for that only on a change of parent, and SPEC-507 offers `POST …/move` for moving contents. <br>• Before M6, a `PATCH` of the position moved only the group. The code computes the offset from any position change | **Probe 1:** `PATCH {x: 300}` moved the group's host from x 100 to 300, with events `group.updated; group.moved` | **Needs the user's decision (D1):** <br>(a) only a change of parent moves the contents; a `PATCH` of `x`/`y` moves just the group, as before (recommended; matches the Spec, and `move` is the way to move contents); <br>(b) every position change moves the contents; update SPEC-501/507/508 |
| C4 | L | **"New host here…" on empty space can land far from its group.** Without a parent, the server picks the network group by IP (SPEC-107) but keeps the clicked position, so the group's frame stretches across the map to reach the host | `CreateHost`: the given `x`/`y` are used with the parent the server picked | **Needs the user's decision (D2):** <br>(a) the GUI sends the position only when the click was inside a frame (a parent is given). Otherwise the server places the host next to the group it picks, or at a free root position (recommended); <br>(b) keep the clicked position |
| C5 | L | **The discovery dialog doesn't focus its range field**, so typing goes nowhere until the field is clicked. Probe 3 typed "127.0.0.0/30" and nothing appeared. Forms already do this (M6 smoke test fix) | Probe 3 | Focus the range field when the dialog opens (unless it is filled in by "Scan this network") |
| C6 | L | **`group.moved` is emitted for an empty group by `POST …/move`, but not by a change of parent.** Harmless, but inconsistent | `MoveGroup` always publishes it; `UpdateGroup` only when the subtree is not empty | Emit it only when the group has contents, in both places; say so in SPEC-507 |
| C7 | L | **Untested paths** (see §1): `api.moveGroup` in its own package, `openMenu`, the empty-space menu, Esc in `onKey` | Coverage | API test in `internal/api` (200, 400, 404, 405); GUI tests for the host menu loading the host, the empty-space and frame-body menus, and Esc |
