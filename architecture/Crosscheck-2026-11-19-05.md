## 1. Code → Spec

| # | Sev | Finding | Proposed fix |
|---|-----|---------|--------------|
| C1 | M | **An older `show()` answer can replace newer data in the details pane.** `show()` applies its answer whenever the selection is unchanged, even when an event or a reload has meanwhile shown a newer record of the host. With a `host.updated` while loading (which sets the host, so the pane is no longer "loading"), then a placement whose reload lands first, the older answer of `show()` comes last: the reviewer's probe showed "Views: Networks" and no description, both stale. A `host.updated` alone overwritten by an older `show()` answer was possible before 2026-11-19-03 too. | Count `show()` among the reads (`reloads`): its answer is applied only if no newer read or event came; otherwise the host is read once more. |
| L5 | L | **Reported as M, downgraded:** a communities dialog of a group stays open when the group's view is deleted, because `DeleteView` sends only `view.deleted` (the reviewer's probe opened the dialog by calling it directly). The GUI offers "SNMP communities…" only for network-view groups (`edit.go`), and the network view can't be deleted, so it can't happen from the GUI. | Close a group's dialog also when the model no longer has the group (covers it, and L1). |
| L1 | L | `openCommunities` can open a dialog for an item deleted while its GET was under way; a second dialog replaces `g.commDialog` without closing the first, which then no longer closes on deletion. | Close the earlier dialog; don't open one for an item the model no longer has. |
| L2 | L | On `host.deleted` the dialog's "the host was deleted" and the deletion's own status message can replace each other. | Keep; cosmetic. |
| L3 | L | The test transport's comment says "a value per held answer"; a second held GET would block on `release`. Fine today. | Say it holds one answer. |
