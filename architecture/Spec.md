# Spec — go-ined

Status: **draft v0.64** (2026-11-18)
Withdrawn IDs are kept and marked ~~withdrawn~~ so they aren't reused.
Every requirement has a stable ID (`SPEC-NNN`). Tests in `Tests.md` reference these IDs.
Keywords: **MUST** = required for v0.1, **SHOULD** = wanted for v0.1 but can slip, **LATER** = out of scope for v0.1.

## 1. Purpose
go-ined is a network monitor loosely modelled on Tkined (Scotty). It splits Tkined's single app into:
- **`ined-server`**: a daemon that holds the inventory (SQLite), discovers hosts in CIDR ranges, pings them in the background, does reverse DNS lookups, and serves a REST + SSE API.
- **`ined-gui`**: a Fyne desktop client that shows hosts and groups (including network groups) on one shared map with live status. Groups can be collapsed and expanded, as in Tkined.
- **`inedctl`**: a command-line client for scripting and testing.

## 2. Assumptions (confirmed by the user, 2026-11-10)
- **A1** Up to about 5,000 hosts per server.
- **A2** Discovery sweeps are IPv4 only. IPv6 hosts can be added by hand (scanning IPv6 ranges isn't feasible).
- **A3** By default the server listens on loopback only. A non-loopback address requires a bearer token.
- **A4** The config file format is TOML. Command-line flags override the config file.
- **A5** v0.1 keeps only the current status, not a status history.

## 3. Cross-cutting requirements

### UI colour and contrast (applies to any GUI/TUI component)
- **SPEC-001** MUST: The default theme is a white background with black text.
- **SPEC-002** MUST: Every foreground/background colour pair has a WCAG 2.x contrast ratio ≥ 4.5:1.
- **SPEC-003** MUST: Contrast presets: `AA` (≥ 4.5:1, default), `AAA` (≥ 7:1), `Max` (21:1, pure black on pure white), and `custom` (a user-given minimum ratio between 4.5 and 21). In `Max`, the palette is black and white only, so status is shown by shape and text alone (SPEC-702 guarantees both). In the GUI, buttons then get a black border, because their background is white like the window's (v0.20).
- **SPEC-004** MUST: The user can change the contrast preset interactively at runtime.
- **SPEC-005** MUST: The contrast preset or custom ratio is read from the GUI config file at startup. A change made in the GUI applies immediately, with no restart, and is saved back to the config file.

### Build / CI
- **SPEC-006** MUST: Every CI action (GitHub Actions or similar) is pinned to a full 40-character commit SHA, with the version in a trailing comment, using the latest workable release. Any exception has its reason documented inline.
- **SPEC-007** MUST (v0.24): **CI.** On every push and pull request, GitHub Actions runs:
  - *check*: `gofmt`, `go vet`, `staticcheck`, `govulncheck`, the cgo-free check (`make nogui-check`) and `go mod verify`;
  - *test*: `go test -race ./...` on Linux with the GUI libraries installed, so the GUI tests run headless;
  - *raw-icmp*: the ICMP tests run as root, so the raw-socket mode is exercised against 127.0.0.1 and ::1;
  - *build*: `ined-server` and `inedctl` without cgo for linux, darwin and windows on amd64 and arm64; `ined-gui` for linux/amd64.
  - *gui* (v0.41, user request; on `main` only): `ined-gui` for windows/amd64, darwin/arm64 and darwin/amd64, and linux/arm64, each built on its own runner (`windows-2025`, `macos-15`, `ubuntu-24.04-arm`) because Fyne needs cgo, and the native binary's `-version` checked. One such build per runner type runs at a time (concurrency group `ci-gui-<runner>`); a newer push replaces one still waiting (v0.59, user request: macOS runners are scarce).
  Tools run at pinned versions (`go run tool@version`), not through third-party actions. The Go version is the `toolchain` of `go.mod` (1.26.11, v0.25), so CI, the release and local builds use the same standard library. Dependabot proposes updates of the actions and the Go modules weekly.
- **SPEC-008** MUST (v0.24): **Release.** Pushing a tag `vX.Y.Z` runs a release workflow. It runs the same checks, builds the binaries of SPEC-007 with the version from the tag (`-version` prints it), packs each as `.tar.gz` (`.zip` for windows) together with `LICENSE`, `README.md`, `Changes.md` and `examples/`, writes `SHA256SUMS`, and publishes a GitHub release with the tag's section of `Changes.md` as its text. Since v0.41 the release also has `ined-gui` for the platforms of the *gui* job: the release is first made as a draft, the GUI jobs on their runners add their archives, and a last job checks that all 11 archives are there, writes `SHA256SUMS` over them and makes the release public. The token is the workflow's own `GITHUB_TOKEN` with `contents: write`, only in those three jobs.

## 4. Inventory and data model
There are two kinds of **items**: host and group. A group with a `cidr` is a **network group**. Items form a tree, and all items share one map.

- **SPEC-101** MUST: A **host** has an id, a unique IP address, a PTR name, an optional manual name, a description, a note, an optional parent group, a monitored flag (default on), a status, and created/updated timestamps.
- **SPEC-102** MUST: A **group** has an id, a name, a description, a note, an optional `cidr` (IPv4 or IPv6), an optional parent group, and a `collapsed` flag. If a group is created with a CIDR and no name, its name is the CIDR; a name can't be changed to empty. Hosts and groups form a **tree**: each item has at most one parent, and an item with no parent sits at the root. With views (§4b) this holds per view (v0.16).
- **SPEC-103** MUST: Moving a group into itself or into one of its own subgroups is rejected (no cycles).
- **SPEC-104** MUST: Deleting a non-empty group is rejected unless the request says what to do with its children: `reparent` (move them to the group's parent) or `cascade` (delete them as well).
- **SPEC-105** MUST: A host's status is one of `up`, `down` or `unknown`. A group's status is the worst status among all monitored hosts in its subtree, in the order `down` > `unknown` > `up`. A group with no monitored hosts in its subtree is `unknown`. Network groups follow the same rule.
- **SPEC-106** MUST: Every item has (x, y) coordinates on the single shared map. A new item gets a free position near its parent; a group's members start one row below it, far enough (120 units) that its labels and, in the GUI, the label strip of its expanded frame don't overlap (v0.19). Rows grow with the group (about the square root of its size, 10–50 per row), so a large group is about square (v0.20). The server rounds every position it saves to one decimal, half away from zero, whichever way it comes (create, PATCH, placements, moves, reflow, copy, import); so does a move's `dx`/`dy` and `group.moved`. 0.1 map unit is under half a pixel at the largest zoom (400 %), so nothing visible changes; an item may move by up to 0.05 units, also where a corner should stay put (SPEC-703) (v0.55, user question; design `Design-positions.md`, P1). Reflow rounds member groups and the shift of their contents too (v0.56, crosscheck 2026-11-18-01 C9). A coordinate beyond ±1,000,000,000 is refused with 400 `invalid_argument` ("position out of range"), also when it would be the result of a move, a new parent, reflow, a copy or an import (then also in a dry run), so no position can become infinite (v0.56, crosscheck 2026-11-18-01 C10).
- **SPEC-107** MUST: A host can be added by hand by giving its IP address (IPv4 or IPv6). If `parent_id` is omitted or null, it goes into the most specific network group whose CIDR contains its IP. If none matches, it goes to the root. Changing the IP later doesn't move the host; `outside_cidr` (SPEC-115) shows any mismatch.
- **SPEC-108** ~~withdrawn~~ (v0.4: separate network objects replaced by network groups, SPEC-113)
- **SPEC-109** ~~withdrawn~~ (v0.4: no host-to-network links)
- **SPEC-110** ~~withdrawn~~ (v0.4: a network group's status follows SPEC-105)
- **SPEC-111** MUST: Every host and group has one plain-text **note**. It is optional, empty by default, and at most 64 KiB. Other text limits: a name is at most 255 bytes, and a description at most 4 KiB.
- **SPEC-112** MUST: A group's `collapsed` flag is stored on the server and shared by all clients. New groups start collapsed. An item is **visible** on the map only if none of the groups above it is collapsed.
- **SPEC-113** MUST: A group's `cidr` must be a valid, unique range in canonical form, with no host bits set. Two network groups can't share the same CIDR.
- **SPEC-114** MUST: A network group nested inside another network group must have a CIDR within its ancestor's range. A create, move or update that breaks this is rejected. Ordinary groups (without `cidr`) can sit anywhere, and hosts can be moved anywhere: network membership is a starting point, not enforced.
- **SPEC-115** SHOULD: A host whose IP is outside the CIDR of the nearest network group above it gets an `outside_cidr` flag in the API. This is informational only.
- **SPEC-116** MUST: Ids of hosts and groups are never reused, not even after the item with the highest id is deleted and the server restarts. The id sequences are stored in the database.
## 4b. Views (M4b, v0.16)
Design: `Design-views.md` (approved 2026-11-10, V1–V6 as recommended). A **view** is one map: one tab in the GUI. Hosts are shared by all views (one status, one note, pinged once); each view has its own groups and its own placement of hosts. Where these items conflict with §4, they take precedence: §4's "tree" and "single map" hold **per view**.

- **SPEC-117** MUST: A **view** has an id, a name, a kind (`network` or `custom`), an `order` and created/updated timestamps. There is exactly one network view, with id 1, created by the server (initial name "Networks"). It can be renamed and reordered but not deleted (409). Custom views can be created, renamed, reordered and deleted by any client; views are shared by all clients (V5). Names are unique and 1–255 bytes. Views are listed by `order`, then id; a new view gets an `order` after all others. View ids are never reused (SPEC-116).
- **SPEC-118** MUST: Every group belongs to exactly one view (`view_id`, default 1), fixed when the group is created. A group's parent must be a group in the same view (400 otherwise). Network groups (with `cidr`) exist only in the network view: a `cidr` in a custom view is rejected with 400 (V2). SPEC-103, 104 and 112 apply within each view.
- **SPEC-119** MUST: A **placement** puts a host in a view: a parent group of that view (or the view's root) and a position. In the network view every host has exactly one placement: its `parent_id`, `x` and `y`, with SPEC-106/107 as before. In a custom view a host has at most one placement (V1), and only where a client put it. Hosts created by hand or by discovery are placed only in the network view (V4). A placement without `x`/`y` gets a free position near its parent (SPEC-106).
- **SPEC-120** MUST: Deleting in a custom view never deletes hosts (V3). Deleting a group with `children=cascade` removes its subgroups and the placements in them; `children=reparent` moves its subgroups and placements to its parent. Deleting a custom view removes all its groups and placements. Deleting a host removes all its placements. In the network view, SPEC-104 is unchanged (cascade deletes hosts).
- **SPEC-121** MUST: Group status (SPEC-105) and visibility (SPEC-112) are evaluated within the group's view, over the hosts placed in that view. A host status change can therefore change the status of groups in several views; each change emits `group.status`. `outside_cidr` (SPEC-115) refers to the network placement only.
- **SPEC-122** MUST: API (additive; today's calls keep their meaning):
  - `GET/POST /views`, `GET/PATCH/DELETE /views/{id}` (`name`, `order`; deleting view 1 → 409).
  - `GET /map?view=<id>`: the items of one view, with the placement's parent and position for hosts. Without `view`, the network view.
  - `PUT /views/{id}/hosts/{host_id}` with `{parent_id, x, y}` adds or moves a host in a custom view; `DELETE /views/{id}/hosts/{host_id}` removes it from the view. For view 1 both return 400: there, use `PATCH /hosts/{id}`.
  - `POST /groups` takes `view_id` (default 1); group JSON has `view_id`. `GET /groups?view=<id>` lists one view's groups; without `view`, all groups of all views, each with its `view_id` (v0.17).
  - Host JSON keeps `parent_id`, `x`, `y`: the network placement.
  - Events (SPEC-502): `view.created|updated` (full view), `view.deleted` (`{id}`, one event; the view's groups and placements go with it), `placement.updated` (`{view_id, host_id, parent_id, x, y}`), `placement.deleted` (`{view_id, host_id}`). Deleting a host emits only `host.deleted`, also for its placements. Cascade or reparent in a custom view emits `placement.deleted` / `placement.updated` and `group.deleted` / `group.updated` per item.
  - `GET /map` returns `view_id` next to `items`; in custom views `outside_cidr` is always `false`.
- **SPEC-123** MUST: Storage: migration 3 adds views and custom-view placements; an existing database is upgraded with all its groups in view 1. A host's network placement stays in the `hosts` table (decision M4b-1). The startup check (SPEC-605) also covers views: a group of a missing view moves to view 1's root, a group or placement whose parent is in another view or missing moves to the root of its view, each with a warning.
- **SPEC-124** MUST: `inedctl view list|add|show|rename|order|rm|place|unplace`, `--view` on `group add` and `group list`. `view show <id>` prints the view and a table of its hosts (with `--json`: the view only). `view place <view> <host> [--parent ID] [--x X --y Y]`; without `--parent` the host goes to the view's root, as with the API's `PUT` (v0.17).
- **SPEC-125** SHOULD (v0.53, user request; design `Design-network-export.md`, N1–N9): **Network export and import.** A group of the network view (usually a network group) can be exported with everything below it as one JSON file: `format` `go-ined-network`, `version` 1, `exported_at`, `server_version`, `from` ("Networks › dc › lan"), the group tree (each group: name, CIDR, description, note, host labels, bar colour, collapsed, position; each host: IP address, manual name, description, note, monitored, watch list by name, position; positions relative to the exported group, with one decimal, also for positions saved before v0.55; v0.55, P2) and, per host, its custom-view placements by view name and group path, with the groups on those paths in `view_groups`. Status, times, PTR names, service checks, IDs and created/updated times stay behind. An import checks the file as API input: format and version, names, CIDRs, IP addresses, watch lists, notes up to 64 KiB, at most 10,000 groups and hosts, 32 levels, no IP address or CIDR twice, no plain group name twice under one parent (v0.54, crosscheck 2026-11-17-01 L1), no unknown keys. It lands below a chosen group of the network view, or at the top level, at a given position or as a new group is placed; the rest keeps its place relative to it, hosts keep the file's parents, and `outside_cidr` is computed as usual. Custom-view placements go to the view with that name; a missing view is skipped and reported, a missing group on the path is made; of two sibling groups with that name in the view, the one with the lowest id is used (v0.54, crosscheck 2026-11-17-01 L2). A **dry run** only reports: what would be created and updated, conflicts, skipped views and warnings (another network group would be a more specific home for the imported CIDR). **Conflicts** are a host with the same IP address, a network group with the same CIDR anywhere in the network view, and a plain group with the same name under the same parent (names match exactly: "Printers" is not "printers"; v0.54, crosscheck 2026-11-17-01 L2); by default any conflict refuses the whole import, listing the first 50. With **update**, matching groups are updated where they are: they keep their parent and position, since moving one would take its other contents along, and each one whose parent differs from the file's gets a warning ("… is updated where it is, in …, not moved below …"); the file's items below such a group go into it, so a new group above it in the file may stay empty. Matching hosts are updated and get the file's group and position. Nothing else on the server is deleted or moved (v0.54, crosscheck 2026-11-17-01 C4). A network group that would not fit inside its enclosing network group (SPEC-114) is an error, also with update. The import is one transaction with the usual events; imported hosts start `unknown` and are pinged, looked up and checked as new hosts are.

## 5. Discovery
- **SPEC-201** MUST: A discovery job takes either an IPv4 CIDR range or the id of an IPv4 network group, and probes every address in the range with ICMP echo. Hosts it finds go into the network group for that range. If no network group with that CIDR exists, one is created (named after the CIDR) under the optional target group, or at the root if none is given. An IPv6 range or IPv6 network group is rejected with 400 (A2). A job whose new network group would break SPEC-114 is rejected with 409 before it starts. Each address gets one echo request, and a second one 200 ms later only if the first gets no answer; each waits up to `monitor.timeout`. Discovery uses the same ICMP prober as monitoring and works even with `monitor.enabled = false`. Without a working IPv4 ICMP mode, `POST /discovery` returns 503 `unavailable` with the reason (v0.11).
- **SPEC-202** MUST: For prefixes /30 and shorter, the network and broadcast addresses are skipped. For /31 and /32, every address is probed.
- **SPEC-203** MUST: The largest allowed range (default /16), the probe rate (default 200 probes/s) and the concurrency are configurable. A range larger than the maximum is rejected. `discovery.rate` must be between 1 and 100,000. A job whose range has more addresses than A1 (5,000) logs a warning, since the server is designed for about that many hosts (v0.12).
- **SPEC-204** MUST: A host that responds is added to the inventory, in the most specific network group inside the subtree of the SPEC-201 group that contains its IP (v0.11; for example, discovering 10.0.0.0/16 puts 10.0.1.5 into an existing 10.0.1.0/24 subgroup). It is added with `monitored = true` and status `up`, with round-trip time, loss and `last_seen` from the probe; monitoring takes over from there. Found hosts are saved in batches of about 1 s, with one `host.created` event per host. An IP address that is already in the inventory is not added twice, and that host is not moved.
- **SPEC-205** MUST: Each discovery job has an id, a state (`running`, `done`, `cancelled` or `failed`) and progress (addresses probed, total, hosts found). A job can be cancelled; hosts found until then are kept. Progress is published as events: `discovery.progress` at most once a second, and `discovery.finished` at the end, both carrying the full job (v0.11). Jobs are kept in memory only, so they are gone after a restart. Job ids are strings `<run>-<n>`. The last 100 finished jobs are kept. A job whose range overlaps a running job is rejected with 409 (v0.11). A probe that fails with an error (for example, no route to the range) counts as probed but not found; the job counts these in `errors`, and `error` gives the first message even when the state is `done`. If saving found hosts fails, the job stops with state `failed` and `error` set; hosts saved before that are kept (v0.12).
- **SPEC-206** SHOULD (v0.57, user question; design `Design-rescan.md`, R1a, R3): **Scanning again on a schedule.** A network group has `rescan`: off (`""`) or an interval, a Go duration from 15 min to 8760 h (`"6h"`, `"24h"`, `"168h"`; shown without zero parts, so `"90m"` is `"1h30m"`). It is set with `PATCH /groups/{id}` (`"rescan": "24h"`, `""` or `"off"` for off; anything else is 400) and only on an IPv4 network group whose range is no larger than `discovery.max_prefix`; otherwise 400, also when a CIDR change or clearing the CIDR would leave a rescan on a group that can't have one (turn rescan off in the same or an earlier PATCH). Only a PATCH of `rescan` or `cidr` is checked: a rescan that a lower `discovery.max_prefix` made too large stays, other edits of the group work, and the scheduler passes it over (SPEC-207) (v0.58, crosscheck 2026-11-18-02 C2). The group also has `rescan_last`, when the last finished scan of its whole range ended (`null`: not yet), and `rescan_found`, the hosts that scan added in its range; both are read-only. They are stored with the group (schema 8) and kept over a restart. A group is **due** when it has never been scanned since its rescan was turned on (turning it on clears `rescan_last`), or when `rescan_last` + `rescan` has passed, or `rescan_last` lies in the future (the clock set back; v0.58, L2); another interval keeps `rescan_last`; another CIDR clears both. A scheduled scan is an ordinary discovery job of SPEC-201–205 by group id, with `scheduled: true`: new hosts are added as by hand (`host.created`), known hosts stay where they are, and hosts that no longer answer are left alone. Every job that ends `done`, scheduled or by hand, sets `rescan_last` (and `rescan_found`) of each group with a rescan whose whole range lies in the job's range, with `group.updated`; a scan of only part of the range doesn't count. `rescan` is not in the export file (SPEC-125), so an import doesn't start scans; group copies to custom views (SPEC-729) have no CIDR and so no rescan.
- **SPEC-207** SHOULD (v0.57; design `Design-rescan.md`, R2): **The schedule's load.** The server checks every 10 s for due groups and starts **one scheduled scan at a time**, the one due longest first (then by group id), with the same `discovery.rate` and concurrency as other jobs; after a restart due groups are thus scanned one after the other, not all at once. A due group whose range overlaps a running job is skipped until that job has ended (and is then not due when that job covered it). A manual job (`POST /discovery`) is never refused because of a scheduled one: an overlapping scheduled job is cancelled first (hosts found so far are kept, SPEC-205) and the manual job starts when it has ended. A scheduled job cancelled with `DELETE /discovery/{id}` skips that round: the group is not started again for its interval. A scheduled job that fails is tried again after 5 min. These waits are kept in memory only, and end when the group's `rescan` or `cidr` changes, so turning a rescan off and on makes it due at once (v0.58, L1). `discovery.scheduled = false` runs no scheduled scans; the groups keep their setting. If discovery is unavailable (SPEC-201), the reason is logged once and the scan is tried at every check. A group that can't be scanned doesn't hold up the others (v0.58, crosscheck 2026-11-18-02 C1): one whose range is larger than `discovery.max_prefix` (lowered after the rescan was set) is passed over with one warning; one whose start fails otherwise waits 5 min, with a warning when the reason changes. A job that ends `done` with every probe failed (for example "network is unreachable") doesn't count as a scan of any group; a scheduled one is tried again after 5 min (v0.58, L3).

## 6. Monitoring
- **SPEC-301** MUST: Every monitored host is pinged in the background every `interval` (default 60 s). `monitor.enabled = false` turns pinging off for the whole server; hosts then keep their stored status and `/health` reports `icmp_mode: disabled` (v0.9). Start times are spread across the interval so the pings don't all go out at once.
- **SPEC-302** MUST: Each round sends `count` echo requests (default 3) with a `timeout` (default 1 s). The requests of a round are at least 200 ms apart, so devices that rate-limit ICMP don't drop them (v0.10). A host is `up` if at least one reply arrives. It becomes `down` after `down_after` failed rounds in a row (default 2). Before its first result, a host is `unknown`.
- **SPEC-303** MUST: Each round records the average round-trip time, the packet loss in percent, `last_seen` (time the last reply arrived, not the end of the round; v0.10) and `last_change` (time of the last status change).
- **SPEC-304** MUST: The server tries unprivileged ICMP first and falls back to privileged (raw) ICMP. The startup log says which mode is in use. If neither works, the server keeps running, marks hosts `unknown` and reports a clear error through the API's health endpoint (`status: degraded`, `icmp_mode: unavailable`, `icmp_error`). IPv4 hosts are pinged with ICMP, IPv6 hosts with ICMPv6 (v0.8). The mode is chosen per address family. If IPv6 ICMP is unavailable while IPv4 works, IPv6 hosts are not pinged, their status isn't changed, and `/health` reports `icmp6_error`; `status` stays `ok` (v0.10). In raw mode, all rounds of one family share one socket, so each reply is received once (v0.10). When no mode works, the message names the commands that allow ping: the sysctl `net.ipv4.ping_group_range` (and `/etc/sysctl.d/` to keep it) and `setcap cap_net_raw+ep` with the binary's path (v0.26). While a family has no working mode, the server checks again every minute and before each discovery job, and uses a mode as soon as one works, without a restart; the log says so and `/health` shows it (v0.27). The replaced prober is closed when the last ping round using it has ended, so a round still running on it finishes however long it takes (v0.31; v0.30 had a fixed two minutes).
- **SPEC-305** MUST: When a host's status changes, the server emits a `host.status` event. Whenever a group's computed status changes, for any cause (a host status change, a move, an add, a delete, or a change to `monitored`), the server emits `group.status` for that group.
- **SPEC-306** MUST: A host with monitoring turned off (`monitored = false`) is not pinged and is left out of group status.
- **SPEC-307** MUST (v0.8): `host.status` is emitted only when a host's status changes or its `stale` flag clears. Changes to round-trip time or loss alone are saved but emit no event. Ping results are written to the database in batches, one transaction about every second.
- **SPEC-308** MUST (v0.9): When a host's IP address changes, its status is reset to `unknown`, its round-trip time and loss are cleared, `last_change` is set if the status changed, and `host.status` is emitted after `host.updated`. The ping streak starts over.
- **SPEC-309** SHOULD (v0.47, user request; design `Design-connect.md`, C1, C7): **Services.** The server finds out which of these a host offers by one TCP connect per port (timeout `services.timeout`, 1 s; no banner, so not a port scan): `ssh` (22), `rdp` (3389), `vnc` (5900), `vnc:1`…`vnc:9` (5901–5909), `http` (80), `https` (443). A monitored host is checked when it has never been checked (so at once when added or discovered) and then every `services.refresh` (6 h); at most 10 hosts at once. Any host is checked on request (SPEC-511). The result is stored with the host (`services`, the names that answered in this order, and `services_checked_at`; schema 6) and kept over a restart; a new IP address clears both (SPEC-308). `host.updated` is emitted when the list changes or on the first check, not for an unchanged periodic result. With `services.enabled = false` nothing is checked. What the server can reach may differ from what a GUI elsewhere can reach (C1); the GUI therefore never disables an entry (SPEC-730). An SNMP check with a list of community strings to try would work the same way (LATER).
- **SPEC-310** SHOULD (v0.50, user request; design `Design-service-alerts.md`, S1–S4, S9): **Watched services.** A host has a `watch` list, empty at first and never filled automatically: names from SPEC-309 (`ssh`, `rdp`, `vnc`, `vnc:1`…`vnc:9`, `http`, `https`) or any TCP port as `tcp:N` (1–65535), case ignored, `tcp:N` stored without leading zeros; at most 20 entries, no port twice (`ssh` and `tcp:22` are the same port). Each watched service of a monitored host is checked by one TCP connect (timeout `services.timeout`) every `services.watch_interval` (default **5 min**, at least 10 s; user's choice); a service is `down` after `services.watch_down_after` failed checks in a row (2) and `up` after one success; at most `services.watch_concurrency` (50) connects at once. A new service is checked within a few seconds. Each has `status` (`up`, `down`, `unknown`), `last_change` and `last_ok`, stored in table `host_services` (schema 7) and kept over a restart. A service starts `unknown`; one given again in a new list keeps its status, matched by port, so `ssh` given again as `tcp:22` keeps it too (v0.54, crosscheck 2026-11-17-01 L4). A new IP address makes them all `unknown` and clears `last_ok`; turning monitoring off makes them `unknown` and stops the checks. The host's own status stays its ping status (SPEC-105). With `services.enabled = false` nothing is checked: at start every watched service that isn't `unknown` is set to `unknown` (with `service.status`) and stays so (v0.54, crosscheck 2026-11-17-01 C3). A check that ends after its service was removed from the list counts for nothing, also when the service is added again meanwhile (v0.54, crosscheck 2026-11-17-01 L7), and also when both happen before the next round of checks: each watching of a service is told apart from an earlier one (v0.56, crosscheck 2026-11-18-01 L8). A host whose ping status becomes `up` again has its watched services checked at once, so a status from while it was down doesn't last a whole interval (v0.51; needed by SPEC-952). The 6-hour check of SPEC-309 is separate and unchanged.
- **SPEC-311** SHOULD (v0.50; design S5): **`service.status`.** When a watched service's status changes, the server emits `service.status` with `{host_id, display_name, ip, name, port, status, last_change, services_down}`, where `services_down` is the host's number of watched services down after the change, as in `/map` (v0.52); also when it becomes `unknown` because of a new IP address or monitoring turned off. Changing the list emits `host.updated` (with the new `watch`), not `service.status`; a client that tracks a service removed from the list sees it gone from `watch`.
- **SPEC-312** SHOULD (v0.60, user request; design `Design-snmp.md`, N1–N3): **SNMP agents.** With `snmp.enabled = true` (default `false`: community strings go out in clear text to every host they are tried on), the server looks for the SNMP agent of each monitored host whose address lies in `snmp.networks` (empty: everywhere), using gosnmp: each community of `snmp.communities` (default `["public"]`), in order, first with v2c and then with v1, asks for the system group (`sysDescr`, `sysObjectID`, `sysContact`, `sysName`, `sysLocation`); the first answer wins. An SNMPv1 agent that answers the request with an error (one name unknown) is asked for `sysDescr` alone; an error to that too is no answer (v0.61). The agent's texts are made one line: control characters (CR, LF, tab, ESC, …) become spaces, runs of spaces one, invalid UTF-8 is replaced, and at most 255 characters are kept (v0.61, crosscheck 2026-11-18-03 C1, C5). The host then has the version, the community and the system values, and the time of the check, stored with the host (schema 9); when nothing answers, version `""` and the time. A host is looked for when never checked, again every `snmp.rescan` (24 h) while nothing answered, at once when its agent stopped answering a value read (SPEC-313), and on request (SPEC-514). At most `snmp.concurrency` (20) hosts are checked at once; each request waits `snmp.timeout` (1 s) and is sent `snmp.retries` (1) more times. host.updated is emitted on the first check, when the version or system values change, and when the values are dropped; finding the same agent again changes only the time, which isn't saved and sends nothing (v0.61, L2). **An agent that stops answering is kept** (v0.61, C3): after 3 value reads in a row without an answer (SPEC-313) it is looked for with every community; while nothing answers, it is looked for again after 1 min, 5 min and 30 min, and only then saved as "no answer". A check on request saves what it finds at once. These counts are kept in memory. **The community is never shown**: not in the API (also not with the full token), the event stream, the export file (SPEC-125) or the log; the log says "SNMP found on 10.0.1.5 (v2c, community 2 of 3)". A new IP address clears the agent and its values (SPEC-308); unmonitored hosts aren't looked at except on request.
- **SPEC-313** SHOULD (v0.60; design `Design-snmp.md`, N4): **SNMP values.** For a monitored host with an agent, every `snmp.interval` (5 min) the server reads `sysUpTime` and, from HOST-RESOURCES-MIB, the average `hrProcessorLoad` over the processors (whole %), and each fixed disk and RAM of `hrStorageTable` with its description, size in bytes and % used (whole %); v2c walks with get-bulk, v1 with get-next. A device without HOST-RESOURCES-MIB has uptime only (CPU `null`, no storage), which is not an error. Only the latest values are kept, in memory: after a restart, and while monitoring is off, there are none until the next read. `snmp.values` (`{host_id, display_name, ip, values}`) is emitted when the values differ from the last ones in a whole percent or a size (uptime and time left out), and on the first read. A read without an answer is tried again after `snmp.interval`; the third in a row starts the search of SPEC-312 (v0.61, crosscheck 2026-11-18-03 C2). `hrProcessorLoad` is defined per processor (each logical CPU) as 0–100 % over the last minute, so the average is the whole machine's load, 0–100 however many CPUs it has; since the average hides one busy CPU of many, the busiest one and the number of CPUs go along (v0.62, user request); a load outside 0–100 comes from a broken agent and is left out, as are storage rows with a negative size or used value or a size beyond 2⁶³ bytes, and % used is at most 100 (v0.61, C4). `sysUpTime` counts hundredths of a second in 32 bits, so the uptime starts again at 0 after 497 days. A check on request (SPEC-514) keeps the values also for an unmonitored host, until monitoring changes or the next check (v0.61, L8).
- **SPEC-314** SHOULD (v0.60; design `Design-snmp.md`, N2): **SNMP settings.** `[snmp]`: `enabled`, `communities` (no empty entry; at least one when enabled), `networks` (CIDRs), `port` (161; 1–65535), `timeout` (> 0), `retries` (0–5), `concurrency` (≥ 1), `interval` (≥ 10 s), `rescan` (≥ 1 min); a bad value is a config error. `server.toml` holds the communities, so it should be readable only by the server's user, as for the tokens. A community longer than 255 bytes is a config error (v0.61, L6). The database holds the communities too: the server makes its file (and the `-wal` and `-shm` files) readable only by its user at every start (v0.61, L13).

## 7. Reverse DNS
- **SPEC-401** MUST: The server looks up the PTR record when a host is added, and then every `dns.refresh` (default 1 h), with at most `dns.concurrency` lookups running at once (default 20). It uses Go's resolver (the system's DNS settings), with 5 s per lookup. At startup, the refreshes of the existing hosts are spread across `dns.refresh`. A changed name is saved and emits `host.updated`. When a host's IP changes, its PTR name is cleared at once and looked up again (v0.11). `dns.enabled = false` turns reverse DNS off; PTR names then stay as stored (v0.11).
- **SPEC-402** MUST: The name shown for a host is its manual name if set, otherwise the first PTR name (without the trailing dot), otherwise its IP address.
- **SPEC-403** MUST: A temporary DNS error keeps the last known PTR name. An NXDOMAIN answer (the name doesn't exist) clears it; a host that has a name keeps it until 3 such answers in a row, looked up again 1 minute after each instead of after `dns.refresh`, and a found name resets the count. Hosts without a name stay on `dns.refresh`. A name that is cleared, changes, or comes back after being cleared is logged at Info (v0.34, crosscheck 2026-11-12-04 D2: one bad answer from the user's DNS dropped names for up to an hour). An answer for an address the host no longer has is ignored, and only saved changes are logged (v0.35, crosscheck 2026-11-12-05 C1). Of several PTR names, the first is used. DNS results never affect a host's status.

## 8. API (REST + SSE)
- **SPEC-501** MUST: The JSON REST API lives under `/api/v1`:
  - `GET/POST /hosts`, `GET/PATCH/DELETE /hosts/{id}`
  - `GET/POST /groups`, `GET/PATCH/DELETE /groups/{id}?children=reparent|cascade`
  - `GET /map`: every item with its type, parent, position, `collapsed` flag, `cidr`, status, `stale` flag, display name, `has_note` flag, `outside_cidr` flag, `monitored` flag (v0.19, for SPEC-712) and, for hosts, `ip` and `services_down`, the number of watched services that are down (v0.50, SPEC-310; 0 for groups). Flags that don't apply to an item type (`collapsed` on hosts, `outside_cidr` and `monitored` on groups) are `false`. A client builds the map from this one response.
  - `POST /discovery` (202 with the new job), `GET /discovery` (every job kept: running and the last 100 finished, oldest first; v0.57, SPEC-206), `GET /discovery/{id}`, `DELETE /discovery/{id}` (cancel; 200 with the job's state at that moment, `discovery.finished` follows). A job has `scheduled` (v0.57): started by its group's schedule (SPEC-206)
  - Group JSON has `rescan`, `rescan_last` and `rescan_found`, and `/map` items of network groups `rescan` (left out when off) (v0.57, SPEC-206)
  - `GET /health`: without a token, returns only `{status, version}`. With a valid token, it also returns the ICMP mode (`unprivileged`, `privileged`, `unavailable` or `disabled`), `icmp_error` and `icmp6_error` when set, the database status, the run id and `access` (`full`, or `read` for the read-only token; v0.49, SPEC-808). `status` is `degraded` when the database fails or no ICMP mode works (v0.10).
  - Moving, repositioning, collapsing, expanding and editing notes are all done with `PATCH` on `parent_id`, `x` / `y`, `collapsed` or `note`. In a `PATCH`, an absent field is left unchanged; `null` is allowed only for `parent_id` (the root) and is rejected with 400 for every other field (v0.17).
  - Views and placements: SPEC-122.
- **SPEC-502** MUST: `GET /api/v1/events` is a Server-Sent Events (SSE) stream. Event types: `host.created|updated|deleted|status`, `group.created|updated|deleted|status|moved` (`moved`: SPEC-507), `map.arranged` (SPEC-510), `discovery.progress|finished` (`finished` includes the final `state`: `done`, `cancelled` or `failed`), `view.created|updated|deleted` and `placement.updated|deleted` (SPEC-122), `service.status` (SPEC-311, v0.50), `snmp.values` (SPEC-313, v0.60), and `resync`.
  Payloads (v0.8): `*.created` and `*.updated` carry the full object (the same JSON as `GET`); `*.deleted` carries `{"id": …}`, one event per deleted item (a cascade delete emits one per host and group); `host.status` carries the full host; `group.status` carries `{"id": …, "status": …}`; `resync` carries `{"reason": …}`. The server sends a keepalive comment every 30 s. The token is sent in the `Authorization` header, as for every other endpoint. A client that falls too far behind gets `resync` and the stream ends. A client that accepts no data for 10 s is disconnected, so it can't hold up the server or its shutdown (v0.10).
- **SPEC-503** MUST: Every event id has the form `<run>-<seq>`. `run` is a random id chosen at server start, and `seq` increases within a run. The server keeps a buffer of the most recent events (`events.buffer`, default 1,000). A client that reconnects with `Last-Event-ID` gets the events it missed. If those events are no longer in the buffer, or the id comes from a different run, the client gets a `resync` event, which tells it to reload the full state. The `resync` event carries the id of the newest event, so a client that reloads and keeps the stream open continues without a gap (v0.8).
- **SPEC-504** MUST: Errors use the right HTTP status code with the body `{"error":{"code":"…","message":"…"}}`:

  | HTTP | `code` | When |
  |------|--------|------|
  | 400 | `invalid_argument` | Malformed JSON, unknown JSON field, `null` for a field that can't be null (v0.17), invalid IP or CIDR, non-canonical CIDR, IPv6 discovery, a `parent_id` that doesn't exist or is in another view, a `cidr` in a custom view, placing a host in view 1, text over its length limit (except notes) |
  | 401 | `unauthenticated` | Missing or invalid token |
  | 403 | `forbidden` | The read-only token (SPEC-808) with any method but `GET` and `HEAD` (v0.49) |
  | 404 | `not_found` | Unknown id in the path, unknown endpoint |
  | 405 | `method_not_allowed` | Method not supported on an existing endpoint (with an `Allow` header) |
  | 409 | `conflict` | Duplicate IP, CIDR or view name, cycle, non-empty group delete, SPEC-114 violation, deleting the network view |
  | 413 | `too_large` | Note over 64 KiB, request body too large |
  | 503 | `unavailable` | The server is shutting down (for example, a new `GET /events` during shutdown) (v0.9) |
  | 500 | `internal` | Unexpected server error |
- **SPEC-505** SHOULD: The server serves an OpenAPI document at `/api/v1/openapi.json`. Details (v0.24): an OpenAPI 3.1 document, written by hand in `internal/api/openapi.json` and embedded in the binary. It is served without a token, like the reduced `/health` (it holds no data). Tests check that it is valid JSON with the required OpenAPI fields, that its paths and methods are exactly the routes the server registers, and that every JSON field of `pkg/apitypes` appears in its schemas.
- **SPEC-506** MUST: A Go client package (`pkg/client`) wraps the REST and SSE API. The GUI and the CLI both use it. The JSON types live in `pkg/apitypes` and are shared by the server and all clients. API errors are returned as a typed `*client.APIError` with the HTTP status, `code` and message. The event stream reconnects automatically (waiting 1 s at first, doubling up to 30 s), resumes with `Last-Event-ID`, and passes `resync` on to the caller (v0.13). It stops for good on a 4xx answer (for example 401) and retries 5xx answers and connection errors. A connection that sends nothing, not even a keepalive, for 75 s is dropped and reopened. Optionally the first connection attempt may fail at once instead of being retried; `inedctl` uses this to report an unreachable server (v0.15).
- **SPEC-507** MUST (v0.21): **Moving a group with everything in it.** `POST /groups/{id}/move` with `{"dx": …, "dy": …}` moves the group and every item in its subtree, in the group's view, by the same offset in one transaction. In the network view that changes the hosts' `x`/`y`; in a custom view their placements. It emits `group.updated` for the group itself and one `group.moved` event `{"id", "view_id", "dx", "dy"}` for everything inside it, instead of one event per item (SPEC-502); clients that keep positions apply the offset or reload the view (v0.22). `group.moved` is emitted only when the group has contents (v0.23). The offset must be finite (400). With `"contents_only": true` only everything inside the group moves, not the group: one `group.moved`, no `group.updated` (v0.29).
- **SPEC-508** MUST (v0.21): **A new parent gives a new position.** When `PATCH` changes an item's `parent_id` (or `PUT` a placement's parent) without giving `x` and `y`, the item gets a free position near its new parent (SPEC-106), as new items do; a group's subtree moves along by the same offset, announced with `group.moved` when the group isn't empty (v0.22). With `x` and `y` given, they are used, and the contents still move along with the group. A `PATCH` of `x`/`y` alone (same parent) moves only the group; `POST …/move` moves it with its contents (v0.23). This changes `inedctl host move` and `group move`, which so far kept the old position.
- **SPEC-509** MUST (v0.21): Host JSON has `views`: the ids of the views the host is placed in, in tab order (the network view always first). It is filled in `GET /hosts` and `GET /hosts/{id}` and in host events. A placement change emits `placement.*` only, so a client that shows `views` reloads the host on `placement.*`.
- **SPEC-510** MUST (v0.28): **Arranging members on a grid.** `POST /views/{id}/arrange` with `{"parent_id": …|null, "cell_width": …, "cell_height": …}` lays out the direct members of a group of that view (null: the view's top level) on a grid of that cell size (map units, 20–5000; 0 means the normal 100 × 80). Members keep their rough order (top to bottom, then left to right); the grid starts where new members go (SPEC-106) and has about √n columns; a member group takes everything in it along. It is one transaction with one `map.arranged` event `{"view_id", "parent_id"}`, and answers `{"view_id", "parent_id", "moved"}`. `inedctl view arrange <view> [--group ID] [--width N] [--height N]`.
- **SPEC-511** SHOULD (v0.47): **Host services in the API.** Host JSON has `services` (array of names, SPEC-309; `[]` when checked and nothing answered, `null` while never checked) and `services_checked_at` (time or `null`). `POST /hosts/{id}/check-services` (no body) checks the host now, saves the result and answers the host; it takes about the connect timeout. Unknown host 404; a host changed or deleted during the check 409; checks turned off 503. `inedctl host services <id> [--check]` prints "ssh, vnc :1 (checked 2026-11-14 14:02:00)", "none (checked …)" or "not checked yet"; `host show` has a Services line.
- **SPEC-512** SHOULD (v0.50; design S5): **Watched services in the API.** Host JSON has `watch`: `[{name, port, status, last_change, last_ok}]` in the order given, `[]` when nothing is watched. `PATCH /hosts/{id}` with `"watch": [...]` replaces the list (SPEC-310); an unknown name, a bad port, a port twice, more than 20 entries, `null` or a non-list is 400 `invalid_argument`. The read-only token gets 403 (SPEC-808).
- **SPEC-513** SHOULD (v0.53; design N10): **Export and import in the API.** `GET /groups/{id}/export` returns the file of SPEC-125 (also with the read-only token, SPEC-808); a group of a custom view is 400, an unknown one 404. `POST /import` takes the file with the query `parent_id`, `x` and `y` (both or neither), `dry_run` and `update` (`true`/`false`), and bodies up to 32 MiB (other requests stay at 1 MiB, SPEC-504). It answers 200 with the report `{dry_run, done, group_id, create, update, conflicts, more_conflicts, skipped, warnings}` (counts of groups, hosts, custom-view groups and placements) when done or for a dry run, and 409 `conflict` with `{error, report}` when refused for conflicts. A bad query or file is 400 `invalid_argument`; the read-only token gets 403. The server logs each import with its counts. OpenAPI and the API examples have both.
- **SPEC-514** SHOULD (v0.60; design `Design-snmp.md`, N5): **SNMP in the API.** Host JSON has `snmp`: `null` while never checked, else `{version, name, descr, object_id, contact, location, checked_at, values}`, `version` `"v2c"`, `"v1"` or `""` (no answer), `values` `null` or `{at, uptime_s, cpu_pct (null without a processor table), cpu_max_pct (the busiest CPU, v0.62), cpus (their number, 0 without a table, v0.62), storage: [{name, kind ("disk" or "memory"), size_bytes, used_pct}]}`. `POST /hosts/{id}/check-snmp` (no body) looks for the agent now and reads its values, saves them and answers the host (the values also for an unmonitored host, SPEC-313); clients wait up to 5 min for it (`client.SNMPCheckTimeout`, v0.61, L11); it can take every community and version times the timeout and retries. Unknown host 404; a host outside `snmp.networks` 400; SNMP off 503 `unavailable` ("snmp.enabled = false"); a host changed meanwhile 409.

## 9. Storage
- **SPEC-601** MUST: Data is stored in SQLite through `modernc.org/sqlite` (pure Go, no cgo). The database file path is configurable.
- **SPEC-602** MUST: The database schema is versioned. Migrations run automatically at startup.
- **SPEC-603** MUST: The current status, round-trip time, packet loss, `last_seen` and `last_change` are saved to the database, so a restarted server shows the last known state. After a restart, every monitored host has `stale = true` until its first ping round completes. Hosts with `monitored = false` are never stale; turning monitoring off clears the flag (v0.9), and turning it back on sets it until the first round completes (v0.10). `stale` is a separate flag and doesn't change the status value.
- **SPEC-604** MUST: The server takes an exclusive lock on its database at startup. A second server on the same database refuses to start at once, with the message "database is in use by another process". The lock is released when the server stops.
- **SPEC-605** MUST: At startup the server checks the tree. A host or group whose parent group doesn't exist is moved to the root, the repair is saved, and a warning is logged for each one. A parent cycle stops the startup with an error, because it needs a manual fix.

## 11. Configuration and security
- **SPEC-801** MUST: The server listens on `127.0.0.1:8470` by default. The address is configurable.
- **SPEC-802** MUST: Bearer-token authentication is optional, but required when the server listens on a non-loopback address: without a configured token, the server refuses to start. When a token is configured, every request without a valid token gets 401, except the reduced `/health` response (SPEC-501). Clients warn (on stderr, or in the GUI's status area) when they would send the token over plain `http://` to a host that isn't loopback (v0.15).
- **SPEC-803** SHOULD: TLS can be turned on by configuring a certificate file and a key file.
- **SPEC-804** MUST: The server shuts down cleanly on SIGINT or SIGTERM. It finishes database writes and closes SSE streams. Order (v0.8, v0.11): cancel discovery jobs and save the hosts found, stop reverse DNS, the service checks (v0.47) and the SNMP checks (v0.60), stop the monitor and flush its pending results, close the SSE streams, stop the HTTP server, close the database.
- **SPEC-805** MUST: Config files and defaults. Precedence: command-line flags, then environment variables (`INED_URL` and `INED_TOKEN`, clients only), then the config file, then built-in defaults. Default paths follow XDG (`$XDG_CONFIG_HOME`, falling back to `~/.config`, and `$XDG_DATA_HOME`, falling back to `~/.local/share`):
  - Server: `go-ined/server.toml`. Database: `go-ined/ined.db` under the data directory.
  - GUI: `go-ined/gui.toml`. CLI: `go-ined/ctl.toml`.
  - Every key and its default is documented in `examples/server.toml`, `examples/gui.toml` and `examples/ctl.toml`, which are the reference.

  | server | `server.listen` | `127.0.0.1:8470` |
  | server | `server.token` | `""` |

  - `host snmp <id> [--check]` (SPEC-312, 313, v0.60): the agent's system values and latest values; `--check` looks now. `host show` has a row "SNMP: v2c · web · CPU 13 %, memory 63 %, / 91 %" ("not checked yet", "no answer (checked …)"). `events` shows `snmp.values` as "host 1 10.0.1.5 web CPU 13 %, memory 63 %, / 91 %"

  The server URL and token come from SPEC-805.

  Shape (v0.13): `inedctl [--url U] [--token T] [--ca-cert F] [--json] [--config F] <object> <action> [flags] [args]`, parsed with the standard library `flag` package. Examples: `host add <ip> [--name N] [--parent ID] [--note T] [--unmonitored]`, `host move <id> <group-id|root>`, `group add [--cidr C] [--name N] [--parent ID]`, `group rm <id> [--reparent|--cascade]`. `discover start` prints the job; with `--wait` it follows the events, shows progress until the job ends, and exits 1 if the job fails or is cancelled (v0.14). `events` prints one line per event (time, type, id, short summary); with `--json`, one JSON object per line: `{"id", "type", "data"}` (v0.14). Global flags are also accepted after the command, and command flags after positional arguments (v0.14). `note set` without text reads stdin and removes trailing newlines (v0.14).
- **SPEC-902** MUST: Output is a human-readable table by default. `--json` prints the API's JSON unchanged. Tables are sorted by ID. Hosts: ID, IP, NAME, STATUS, RTT, PARENT, MON, SVC (v0.50: `-` when nothing is watched, `2 down` when any watched service is down, `ok` when all are up, else `unknown`). Groups: ID, NAME, CIDR, STATUS, PARENT, COLLAPSED (v0.13), VIEW (v0.17); `group show` includes the view. A stale host shows `(stale)` after its status, so the status is always in words (v0.14).
- **SPEC-903** MUST: Exit codes: `0` OK, `1` the API returned an error (or a waited-for discovery job failed or was cancelled), `2` usage or config error (bad config file, URL or CA file), `3` connection, TLS or authentication error (including 401), `130` interrupted with Ctrl-C (`events` exits 0 instead). After an interrupted `discover start --wait`, inedctl says that the job keeps running on the server. `health` exits 0 whenever the server answers, also when its status is `degraded`; scripts read `--json` (v0.15).
- **SPEC-904** SHOULD (v0.50; design S5): **`host watch`.** `inedctl host watch <id>` prints the watched services ("ssh up, https down since 14:07:10, tcp:5432 unknown", the date added when not today; "none"); with a comma-separated LIST it sets them (an empty LIST is a usage error, so an empty variable in a script doesn't clear the list; v0.54, crosscheck 2026-11-17-01 L5), `--add` and `--remove` change the current list (adding one that is watched already does nothing, also under another name for the same port, such as `tcp:22` with `ssh` watched; v0.56, crosscheck 2026-11-18-01 L6; removing one that isn't watched is a usage error), `--clear` watches nothing; only one of these at a time. It prints the result. `host show` has a "Watched" line in the same form.
- **SPEC-905** SHOULD (v0.53; design N10): **`group export` and `import`.** `inedctl group export <id>` prints the file of SPEC-125, or writes it with `-o FILE` (mode 0600, since notes can be private; also when the file exists, v0.54, crosscheck 2026-11-17-01 L3; a device or pipe such as `/dev/stdout` keeps its mode, v0.56, crosscheck 2026-11-18-01 L7) and says what it wrote. `inedctl import FILE` (`-` = stdin) sends the file as it is, so the server sees unknown keys, and prints the report: "Would create:"/"Created: 2 groups, 2 hosts, 1 custom-view group, 1 placement.", "Updated: …", "Skipped: view \"Lab\" doesn't exist (1 placement).", "Warning: …", "Conflicts: none." or the conflicts, "Imported as group 12.". It exits 1 when the import is, or would be (`--dry-run`), refused for conflicts; a file that can't be read or isn't JSON is a usage error (2). `--json` prints the report as the API returns it.

## 12b. Alerting (`ined-alert`, v0.49, user request; design `Design-alerting.md`, A1–A11)
- **SPEC-950** SHOULD: **The program.** `contrib/ined-alert/` holds `ined-alert`, a Python 3.11+ program using only the standard library, with a client package `ined` (`Client(url, token)`: `hosts()`, `host(id)`, `groups()`, `views()`, `map(view)`, `health()`, `events()`, which reconnects after 1 s doubling to 30 s and resumes with `Last-Event-ID`; a 4xx answer raises `APIError`), an example `alert.toml`, a systemd unit and tests (`make alert-test`, also in CI with the runner's Python 3.12). It is not in the release archives. `ined-alert [--config F] [--check | --test-mail]`: `--check` prints the token's access, the hosts each route covers and the route warnings (exit 1 when there are any); `--test-mail` sends one mail to the admins. Exit codes: 0 stopped by SIGINT/SIGTERM or a check that went well, 1 a runtime error such as a refused token, 2 a configuration error. With the full token it warns and still runs. A token the server doesn't accept is named so in the warning (authenticated `/health` fields missing), apart from an older server that doesn't say what the token may do (v0.54, crosscheck 2026-11-17-01 L9).
- **SPEC-951** SHOULD: **Config.** `alert.toml` (default `$XDG_CONFIG_HOME/go-ined/alert.toml`): `[server] url, token` (`INED_URL`, `INED_TOKEN` override); `[mail] host` (`localhost`), `port` (25), `from` (required); `[alert] admins`, `down_after` (`2m`), `batch` (`30s`), `repeat` (`""` = none), `startup_summary` (false), `state_file` (`""` = `$XDG_STATE_HOME/ined-alert/state.json`), `server_down_after` (`5m`); `[[route]] group, to`; `[syslog] address` (`""`, `udp://h:p`, `tcp://h:p` or a socket path), `facility` (`local0`); `[log] level` (`info`). Durations as Go writes them. An unknown section or key, a bad duration or address, a missing `from`, or neither admins nor routes is an error.
- **SPEC-952** SHOULD: **What is alerted.** A monitored host whose status becomes `down` and stays down for `down_after` (counted from its `last_change`) gets a **down** alert; before it is sent the host is read from the server once more, so an old event can't cause one. When the host is `up` again (also checked with the server; when the server can't be asked, the alert stays open and the server is asked again at the next tick, as for a down alert; v0.54, crosscheck 2026-11-17-01 C2), the recipients of the down alert get a **recovery** alert. Back up within `down_after`: nothing, only logged. `unknown` is not alerted per host and ends a waiting alert. Turning monitoring off or deleting the host ends an alert without a mail. No repeat unless `repeat` is set ("STILL DOWN"). **Watched services** (SPEC-310, v0.51; design `Design-service-alerts.md`, S8) are alerted the same way, from `service.status` and the hosts' `watch` lists: down for `down_after`, checked with the server, then recovery, with the host's recipients. While the host is `down`, or waiting for its own down alert, its service alerts wait (logged once as `held`); a service still down when the host is back is alerted `down_after` after the host's `last_change`. A service alert already open when the host goes down stays open, without repeats while the host is down, and gets its recovery later. A service no longer watched, monitoring off, the host deleted or the service becoming `unknown` (the server's checks turned off, a new IP address; v0.56, crosscheck 2026-11-18-01 C11) ends a service alert without a mail, and so without STILL DOWN repeats. Hosts from a server without watched services (no `watch`) are handled as before; open service alerts of such a host are closed without a mail at the next snapshot (a server downgraded below v0.50; v0.54, crosscheck 2026-11-17-01 L8). A service alert whose service is watched under another name for the same port keeps going under the new name (v0.54, crosscheck 2026-11-17-01 L4).
- **SPEC-953** SHOULD: **Recipients.** A route names a group by its path, view first (`Networks/dc/lan`, `Payroll/app servers`), or a whole view (`Payroll`), and covers the group and everything below it. A host's recipients are those of every route covering it in any view, plus the admins; each recipient gets an alert once. Routes are resolved from the views and their maps, again a few seconds after group, view, placement or host changes. A route that matches nothing, or several groups (it covers them all), or has no recipients (`to = []`; v0.54, crosscheck 2026-11-17-01 L10), is a warning in the log.
- **SPEC-954** SHOULD: **Mail.** Alerts for one recipient within `batch` go out as one plain-text mail ("[ined] DOWN web (192.0.2.10)", "[ined] UP web (192.0.2.10) after 18 min", "[ined] 40 hosts down in Networks/dc"; for services, v0.51: "[ined] DOWN https on web (192.0.2.10)", "[ined] 2 hosts down, 3 services down in Networks/dc", with the port and "last answered" in the body), with name, IP address, the host's groups as paths, since when, last seen and the server URL; header `Auto-Submitted: auto-generated`. Sent through SMTP without login or TLS; a failure is retried after 10 s, 1 min and 5 min, then dropped and logged as an error (`mail_dropped`). The alert counts as sent once its mail is queued: after a dropped DOWN mail the alert stays open, and its recovery mail still goes out (v0.54, crosscheck 2026-11-17-01 C6; sending dropped mail again is LATER, as the relay is local). At a stop, what is waiting is sent first.
- **SPEC-955** SHOULD: **Logging.** Every action (start and stop, connected, disconnected, `resync`, each status change seen, an alert waiting, cancelled, queued, sent, failed or dropped, config warnings) is one `key=value` line on stderr and, with `[syslog] address`, to a syslog collector with tag `ined-alert`. A collector that can't be reached is reported once; alerting goes on. Only the first of a series of failed reconnects is a warning.
- **SPEC-956** SHOULD: **Restart and the server's state.** A state file (JSON, written atomically, mode 0600; version 2 since v0.51, which adds the open service alerts under `services`; version 3 since v0.63, which adds the open threshold alerts under `thresholds` (SPEC-958); versions 1 and 2 are read as before) holds the open down alerts and whether the admins were told the server is unreachable or degraded. At start and after `resync`: a host down with an open alert gets nothing new, a host down without one is alerted after its delay, an open alert for a host that is up gets a recovery mail, one for a deleted host is closed. An unreadable state file is moved to `.bad` and logged; so is one of the wrong shape or of a version above 2, and the program starts without open alerts (v0.54, crosscheck 2026-11-17-01 C1). The same holds for open service alerts: recovery for a service up by now, closed for one no longer watched or a host deleted. `startup_summary` mails the admins the monitored hosts down at start, and the watched services down on the other hosts (v0.51). When the event stream is lost for `server_down_after`, or `/health` (read every 60 s) says `degraded` that long, the admins get one mail, and another when it is over.
- **SPEC-957** SHOULD (v0.57, user question; design `Design-rescan.md`, R5a): **New hosts.** With `[new_hosts] enabled = true` in `alert.toml` (default `false`), every `host.created` (a host found by a scan, scheduled or not, imported or added by hand) is mailed as **new** to the admins and the recipients of the routes of its groups, once the routes have been loaded again after the event (SPEC-953; a few seconds), batched like the other alerts: "[ined] NEW printer-3 (10.0.1.7) in Networks/lan", several "[ined] 3 new hosts", mixed "[ined] 1 down, 1 new host"; the body has "NEW  printer-3 (10.0.1.7) added at 14:02:05" and the groups. A host deleted before that isn't mailed. New hosts aren't kept in the state file, and hosts that only a `resync` shows (after a long disconnect or a restart of the server or of `ined-alert`) aren't mailed; after a short disconnect the client resumes with `Last-Event-ID` and gets them (v0.58, crosscheck 2026-11-18-02 P2). The host is alerted as any other too.
- **SPEC-958** SHOULD (v0.63, user request; design `Design-snmp.md`, N7, N8; `Design-alerting.md` A10): **SNMP thresholds.** `[[threshold]]` in `alert.toml`: `metric` (`cpu`, the average over the CPUs; `cpu_max`, the busiest CPU; `memory`; `disk`, each fixed disk by name), `above` (a percentage, 0 to below 100) and `for` (default `"5m"`); no rules unless written (the example has two commented out); anything else in a rule is a config error. A value above its line (from `snmp.values` events, and from the hosts at start and after a `resync`) waits `for`; then the host is read from the server once more and, when the value is still above, a **HIGH** alert goes to the host's recipients (SPEC-953): "[ined] HIGH disk / 91 % on web (10.0.1.5)". At or below the line again within `for` cancels it (logged); after a HIGH it sends **OK**: "[ined] OK disk / 78 % on web (10.0.1.5) after 2 h". `repeat` sends "STILL HIGH … for 4 h". With two rules for one metric the lower line counts. When the host's values go away (no agent, monitoring off, the server restarted and not read yet) or the host is deleted, its threshold alerts end without a mail (logged). Batching, mixed subjects ("1 down, 1 value high, 1 value OK again"), the body ("HIGH  disk / 91 % (above 90 %) on web (10.0.1.5) since …", "OK  … (at or below 90 %) …", groups) and syslog work as for the other alerts. Open threshold alerts are kept in the state file (version 3, `thresholds`, keyed `host id/metric/item`; SPEC-956).
